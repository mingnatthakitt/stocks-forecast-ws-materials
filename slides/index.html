fundamentals · 1We predict returns, not prices

Prices trend, drift, and live at ever-different levels. A model trained on 2014 levels is useless at 2024 levels — and NVDA's raw chart contains a 10:1 split cliff in 2024 that would look like a −90% "crash".

Returns are comparable across tickers and decades — stationary-ish, centered on zero, and the honest target of forecasting. We model five instruments: SPY, NVDA, AAPL, MSFT, TSLA.

Rt+1 = (Pt+1 − Pt) / Pt

Given: everything known up to Tuesday's close
(prices, volume, indicators you compute)

Predict: Tuesday → Wednesday return

Never allowed: any feature that peeks at Wednesday. That's leakage — it inflates your validation and dies on the private set.

ml from zero · 1What a "model" actually is

Nothing mystical. A model is just a function: numbers go in, one number comes out. The only difference from a calculator is that nobody wrote the instructions — the machine worked them out from examples.

featurethe inputs · what it knows
A number you already know at the moment you have to predict. Yesterday's return, the 20-day average, how crowded the stock is. Today's notebook ships you about 15 of them.
labelthe answer · what you want
The number you're trying to produce, and the one you cannot see yet. Here it's always the same thing: tomorrow's return.
predictionthe guess · ŷ
What the model says the label will be. A single number, per stock, per day — so "portfolio of 5 tickers" = 5 numbers a day.
errorhow wrong it was
The distance between guess and truth. This is the only thing that drives learning: every model we use today exists to make this number smaller on days it has never seen.

In code this is the whole contract: def predict(df) -> pd.Series. Feed it a dataframe of features, get back a series of tomorrow's returns. Every architecture today obeys the same contract — only the maths inside differs.

ml from zero · 2How it learns: guess, check, adjust

This loop is all there is. Nobody tells a model the rules of the stock market — it discovers them by being wrong, a few million times.

step 1
Guess
It has never seen today, so it produces a number anyway. Early on this is close to nonsense.
→
step 2
Check
The true answer arrives. It measures the error — how far off it was.
→
step 3
Adjust
It nudges its internal dials, so that being wrong this way becomes less likely next time.
↻
repeat
10,000×
Nine years of trading days, five tickers at once. Each error a small correction.

The dartboard in the dark. You can't see the board. Someone watches where you land and says only "too high, too far right". You adjust by that much and throw again. After ten thousand throws you're a good dart player — nobody ever taught you the geometry. Every model on the next slides is just a different way of holding that memory.

This is also why the loop needs data with answers attached — you cannot learn from a guess, only from a guess that got checked.

ml from zero · 3The one failure mode that matters: memorising

generalising · the goal

A student who understands the material. Given a fresh question they've never seen, they still get it right — because they learned the underlying pattern.

Reads as: fine on the days it trained on, and still fine on new days.

memorising · the failure

A student who memorised the textbook. Perfect on last year's questions, and lost the moment the exam changes a single word.

Reads as: brilliant on the days it trained on, and helpless on new ones.

in your notebook, this is the train-vs-val gap

Memorising: train MAE ≪ val MAE. It has learned 2014–2022, noise and all — and 2023–24 is new material. Fix: regularise (shallower trees, more dropout, fewer epochs, bigger alpha) or improve the features. Adding more training days of the same kind usually does not help.

Underfitting is the opposite and much rarer: both train and val are bad, because the model is too simple to see anything. Fix: more capacity, more epochs, better features.

The trap: a memorising model is hard to spot on the data you trained it with. That's exactly why we hold 2025 back.

ml from zero · 4Two kinds of numbers: the ones it learns, the ones you set

parametera gear · learned by the model
A number inside the model. Thousands of them. Nobody types them in and nobody sees them — the training loop moves every one of them, and they're the model's entire memory of the market.
hyperparametera dial · set by you
A number you choose before training, and which training cannot change by itself: max_depth, epochs, alpha, seq_len. This is the competition.
neural-net dialplain meaningturn it and…
seq_lenhow many days of history the model reads at oncelonger = more context, slower, more to memorise
epochshow many times it studies the whole training setmore = better fit until it starts memorising
lrthe step size it takes when correcting itselftoo high = overshoots and diverges; too low = learns too slowly
batch_sizehow many days it looks at per correction — mostly speedbigger = steadier, needs more memory
hidden_sizehow much scratch memory the model hasbigger = more capacity, and more ways to overfit

A layer is one stage of that processing — raw numbers in, slightly more abstract numbers out, repeated a few times. That's all a "deep" neural network is: a short stack of layers.

model A · the underdogLinear / Ridge regression

ŷ = w₁x₁ + w₂x₂ + … + wₙxₙ + b
Strengths
  • trains in milliseconds
  • honest — very hard to overfit badly
  • readable: every weight is a claim about a feature
  • a strong baseline that punishes bad features
Weaknesses
  • only straight-line relationships
  • no interactions between features
  • garbage in, garbage out — it has no tricks

Your knobs: alpha (regularisation — bigger = flatter) and, above all, the features you feed it. Underdogs win this workshop surprisingly often.

model A · plain termsRidge is a line through the data

12 features → 12 multipliers → add them up → one number
"if yesterday's return was +2%, and its weight is 0.3, add +0.6% — then repeat for the other 11"
what it does well

Each weight is a single, readable number. After training, "0.3 on yesterday's return, −0.1 on volume spike" is a sentence you can argue with. It takes milliseconds, and it is very hard to make it break.

what it cannot express

It can only draw straight lines. No matter what, "high volatility and falling" can never become "high volatility unless it's also rising". Features act one at a time — never in combination.

so when do you use it?

First, always — it's your honest reference point and it runs instantly, so you can change one feature and see the effect immediately. Then keep it if it wins. The underdog genuinely wins workshops like this one, because on noisy financial data a simpler model is often the more honest one.

alpha is the brake on the weights: bigger = flatter, safer, duller. If your weights are exploding into huge cancelling numbers, turn it up.

model B · the committeeRandom Forest — many trees, one vote

dataset → tree · tree · tree · … · tree
each tree sees a random slice, overfits in its own way → averaging cancels the madness
Strengths
  • captures nonlinearities & interactions
  • robust defaults, hard to crash
  • great on tabular data with zero preprocessing
Weaknesses
  • sees one day's snapshot — time flows past it
  • big forests get slow and memory-hungry
  • deep trees memorise noise fast

Your knobs: n_estimators max_depth min_samples_leaf max_features

model B · plain termsOne tree is a flowchart. A forest is 200 of them.

"volatility high? → yes → check the 20-day trend → yes → predict +0.4%"
that whole chain of if/then is ONE tree. Build 200 of them, each on a random slice, and average.
why averaging is the whole trick

Each tree is slightly wrong in its own way — it memorised a quirk of the slice it saw. Those quirks are random, so when you average 200 of them they cancel out. What's left is the part they all agreed on: the real pattern. A committee of individually mediocre experts becomes a good one.

what it fixed over Ridge

It can draw wiggly, branching boundaries instead of straight lines — and it handles combinations ("high vol AND falling") that Ridge structurally cannot.

what it still can't see

Time. Each tree sees one day's snapshot, like a photograph. "The last 3 days fell" is invisible to it unless you hand that fact over as a feature — which is exactly what your feature list does.

max_depth = how many if/then steps deep a tree may go (deeper = more detail, more memorising). min_samples_leaf = how many days must agree before the tree believes a split.

model C · the tabular kingXGBoost — trees that fix each other

Forest (bagging)

trees vote independently, errors average out.

Boosting

each new tree is trained on the errors of the ensemble so far — a queue of specialists correcting the last one's mistakes.

Strengths
  • state of the art on engineered tabular features
  • flexible: regularisation built in everywhere
  • fast on CPU, scales to your features
Weaknesses
  • overfits eagerly — respect max_depth
  • many interacting knobs to tune
  • still just a snapshot learner

Your knobs: n_estimators max_depth learning_rate subsample colsample_bytree reg_lambda early_stopping_rounds

model C · plain termsXGBoost: each tree is handed the last one's mistakes

tree 1 predicts → "here's where I'm wrong" → tree 2 is built to fix exactly that → …
300 trees, each one a small correction aimed at the errors that are still left. A relay race of specialists.
why it's usually the strongest here

A forest corrects itself by averaging — it throws away how wrong it was. Boosting keeps the errors and aims the next tree straight at them. On well-built tabular features that reliably beats averaging. It's the pragmatic winner: fast on a CPU, no scaling needed, and the knobs are deep.

the cost of aiming

Aiming at your own mistakes is a double-edged trick: left alone for enough rounds it will eventually fit the noise perfectly. It overfits eagerly — keep max_depth shallow (3 is a good start) and treat every extra tree as a cost, not a free win.

so when do you use it?

When you've already got good features and Ridge/Forest are plateauing, and you have time to watch the val curve. Don't start here — it's the most fiddly of the five and the least forgiving of a rushed tuning session.

learning_rate = the step size: lower + more trees is nearly always better than high + few, and much harder to overfit.

model D · the sequence readerLSTM — memory with gates

day t−19 → … → day t−2 → day t−1 → today ⇣ tomorrow
a rolling window of the last seq_len days, read in order, state carried forward
Strengths
  • designed for ordered, sequential signal
  • can (in principle) learn temporal dependencies
  • the "deep learning" option — worth trying honestly
Weaknesses
  • slow to train, hungry for tuning
  • needs scaling + careful windowing
  • on noisy daily returns it memorises fast — watch the overfit ratio

Your knobs: seq_len hidden_size num_layers dropout epochs lr batch_size

model d · plain termsThe sequence reader: a notebook carried forward

day t−19 → … → day t−1 → today ⇣ tomorrow
one window, read left to right, one day at a time — and a notebook of what it has noticed so far
the "gates" — three yes/no questions per day

forget? is yesterday's spike still relevant today? → erase it
write? is this new info worth a note? → add it
use? which note do I actually answer from? → read that one out

That notebook is the model's memory. It's why an LSTM can notice "three red days in a row" while a forest — which only ever sees today's snapshot — cannot.

what it finally adds

It is the only one of the five that reads the order of days. If a pattern genuinely lives in the sequence — a shape, a rhythm, a slow drift — this is the one that can see it.

the honest warning

It is the easiest model here to memorise with. Millions of dials, a small dataset, and daily returns that are mostly noise. It will fit 2014–22 beautifully and then meet 2023 and fall apart. Watch the gap, not the score.

The honest truth for this data: it is worth trying, and it is often worth losing to Ridge. The teaching point is that you earn that conclusion by running it, not by assuming.

Needs the numbers scaled before it works (the notebook does this for you) — a neural net fed a price of 500 behaves very differently from one fed a return of 0.5.

model E · the gambitWildcard: GRU or 1D-CNN

GRU — the lean recurrent

The LSTM's cheaper cousin: fewer gates, faster training, similar memory. Pick it if you want a sequence model without the LSTM's moodiness.

1D-CNN — the pattern spotter

Convolution filters slide over the window hunting local shapes — 3-day dips, volume spikes. No memory, just pattern matching. Fast and surprisingly decent.

In the notebook, set WILDCARD_ARCH = "gru" or "cnn" — one line switches the whole model.

Draft rule: wildcard slots are capped — choosing the road less travelled has its privileges.

model e · plain termsTwo cheaper ways to read the same window

gru · the same idea, fewer questions

An LSTM asks three questions per day (forget / write / use). A GRU asks two — it merges the forget and write decisions into one. Less bookkeeping, so it trains noticeably faster and holds roughly the same memory.

Pick it when you want the sequence reader without the moodiness and the waiting.

1d-cnn · the pattern spotter

No memory at all. Instead it slides a small stencil across the window — the same idea as the filters that read handwritten digits — and asks "does a 3-day dip look like this? a volume spike like this?"

It only ever sees local shapes, never a long arc. Fast, and on some data genuinely good.

the shared limitation

Both read the same seq_len-day window the notebook hands them — and both are just as vulnerable to memorising as the LSTM. A fancier reader is not automatically a better one. You are choosing a different way to look at the same information, not extra information.

One line switches between them: WILDCARD_ARCH = "gru" or "cnn". Try both — that's the point of the wildcard slot.

so which one?Pick by your time, not by the name

modelreach for it whenavoid it when
Ridge you're starting, or you changed a feature and want a instant read on it you suspect the effect curves or depends on combinations
Forest you want a strong result with no tuning — sane defaults, hard to break training gets slow and memory hungry (big forests)
XGBoost features are good and Ridge/Forest have plateaued; you have time to watch val you're in a hurry — it overfits eagerly if you let it run

the honest answer

On this data the rankings barely move. Our own demo run: the forest had the best MAE (0.01598) and made +25.7% — but the GRU had the worst MAE (0.01624) and made +27.5% on 322 trades, because it traded far more often. Add a 10 bps trading cost and the churn bites: the GRU collapses to +19.6% while the barely-trading forest barely moves (+24.8%). Accuracy is not profit, and profit is not free. Measure the thing you're actually graded on.

crash course · featuresFeatures beat architecture

The starter menu (all computed from the past only)

return_1d / 5d / 10dlagged returns sma_ratio_5_20ema_gap_12_26 rsi_14volatility_10/20 volume_ratio_5range_pct momentum_20dist_high_60

A simple model with great features beats a fancy model with lazy ones. This is where competitions are won.

The three commandments
  • no shift(-1) — that's the future, i.e. the answer
  • no target-derived columns (a "volatility" computed from tomorrow)
  • rolling windows are fine — they only look backwards

Ideas: day-of-week, distance to 52-week high, consecutive up-days, overnight vs intraday split… the add_features() cell is yours.

1:28 · paper tradingA prediction is not a trading algorithm

An ML prediction is…

one number per (day, ticker): tomorrow's expected return. It says nothing about whether to trade, how much to bet, or what acting costs.

A trading algorithm adds…

entry/exit rules, position sizing, transaction costs, risk limits — decisions the model never made. Same predictions + different rule = different P&L.

One simple rule, applied to your predictions

pred > 0 → LONG · else CASH
